# 06 版本与兼容

状态:草案

回答:**更新 Core 之后,已有的 Pack 数据和存档怎么办?**

## 1. 总原则

- Core 与数据文件之间隔着 Content 层。**文件格式的变化由 Content 吸收**,Core 只认标准化的内存模型。
- 不同类型的变化用不同的版本号和机制处理,不混在一个"版本"里。
- 存档现阶段**不做迁移**:不兼容就拒绝并说明原因。待规则稳定后再设计存档迁移。

## 2. 四个版本号

| 版本号 | 属于 | 位置 | 何时变化 | 谁负责兼容 |
|---|---|---|---|---|
| `formats.<kind>` | 数据文件 | `pack.json`;每个文件的 `schema` 字段 | 文件结构变了 | Content 层**迁移器**:加载时在内存升级,不改作者的文件 |
| `capabilities` | 引擎能力 | `EngineInfo`;`pack.json` 的 `requires` | 新增能力(如新脚本 API 版本) | **只增不改**;缺少能力时加载前失败 |
| `behaviorVersion` | 引擎行为 | `EngineInfo`;写入存档 | 同一份数据的运行结果变了 | **兼容开关**,否则拒绝 |
| `saveSchema` | 存档结构 | 存档文件头 | 存档结构变了 | 现阶段:不等则拒绝 |

另有 `engineVersion`(如 `0.3.0`),仅用于显示和 `requires.engine` 的范围判断。

## 3. 改动分级

| 类型 | 例子 | 对旧数据的影响 | 合并条件 |
|---|---|---|---|
| **新增** | 加字段、加技能效果、加能力 | 无 | 新字段默认值 = 旧行为;如新增能力,登记到 `capabilities` |
| **结构改动** | 字段改名、一张表拆成两张 | 旧文件读不了 | **必须同时提供迁移器**,并升该类内容的 `schema` |
| **行为改动** | 修正伤害公式、AI 调整、平衡 | 同样的数据结果不同;进行中的存档会走样 | **必须提供兼容开关**,或升 `behaviorVersion` 并标注为不兼容改动 |

没有满足合并条件的改动,不允许合入。

## 4. 迁移器(数据)

- 位置:Content 层,按内容类型注册。
- 形式:`Migrate(kind, fromSchema) → toSchema`,逐版本串联(v1→v2→v3)。
- **只在内存中升级。** 作者的原文件不被改写;想固化时由编辑器提供"升级并保存"。
- 指纹基于源文件字节计算,不受迁移影响。

```csharp
// 草案
public interface IContentMigration
{
    string Kind { get; }
    int From { get; }                    // 升到 From + 1
    JsonNode Migrate(JsonNode document); // 输入输出均为 JSON 文档
}
```

## 5. 兼容开关(行为)

项目里已有这类做法(`correctOriginalEquipment`、"显式兼容选项可复现原包")。把它正式化:

- 每个开关有**稳定的名字**、说明、引入版本,登记在 `EngineInfo.KnownCompatFlags`。
- 默认走最新行为;开关打开时保留旧行为。
- 一局开始时,**把本局使用的开关集合写进存档**。读档时按存档里的集合继续,因此"老局按老规则打完"。
- 开关集合来自两处:Pack 声明(`pack.json` 的 `compat` 字段)和引擎默认。Pack 的声明优先。
- 无法用开关保留的行为改动 → 升 `behaviorVersion`,读档时若存档版本不同且开关无法还原,拒绝。

**开关的生命周期:** 每个开关在引入时写明"计划移除版本"。过了期限仍无人使用,从引擎删除,同时升 `behaviorVersion`。避免 Core 长期背着历史包袱。

## 6. 存档兼容(现阶段)

| 情况 | 结果 |
|---|---|
| `packId` / 指纹不同 | 拒绝 |
| `saveSchema` 不同 | 拒绝 |
| `behaviorVersion` 不同,且开关能还原 | 按存档中的开关继续 |
| `behaviorVersion` 不同,开关不能还原 | 拒绝 |

- 拒绝时给出**可定位的原因**(哪个版本号不符、当前是多少、存档是多少)。
- 存档迁移器(旧 `saveSchema` → 新)留到规则稳定后再设计。在此之前,每次变更存档结构都视为不兼容并升 `saveSchema`。

## 7. 回归保障:旧数据包语料库

升级 Core 之前,必须在一组**固定的旧数据包**上通过检查:

| 语料 | 来源 |
|---|---|
| 原版 `base` | 由导入器生成 |
| 示例 Mod | `docs/import/mod-kit/examples/*` |
| 民国 Mod | `docs/product/mingguo-mod-plan/`（策划） |
| 真实 Mod | 已验证过的兼容样本(见旧 `reverse/MOD_RESOURCE_COMPAT_20261019.md`) |

每个语料包需通过:**加载 → 校验(到 `SmokeStart`)→ 一组关键行为快照一致**。

- 快照沿用旧 `Ew4.Verify` 的做法(固定输入 → 固定输出)。
- 只有**有意**改变行为时才允许更新快照,且必须同时满足 §3 的合并条件。

## 8. 脚本 API 的版本

- 脚本 API 版本(现有 `apiVersion` 1、2)属于 `capabilities`。
- **已发布的版本不删除、不改语义。** 新能力开新版本号。
- Pack 在 `requires.capabilities` 里声明需要的版本;引擎不支持时加载前失败。

## 9. 作者视角

| 场景 | 作者需要做什么 |
|---|---|
| 引擎只加新功能 | 什么都不用做 |
| 数据格式升级 | 通常什么都不用做;想固化可点"升级并保存" |
| 引擎有行为改动 | 旧 Mod 照常运行(靠兼容开关);作者可选择改用新行为 |
| Mod 需要新能力 | 在 `requires` 里声明;旧引擎会在加载前提示"需要升级" |
