# 原版逻辑的阶段性逆向记录

更新：2026-10-18。当前成果是旧资源导入、反编译证据和规则研究，尚无重写版引擎或APK。
以下地址均为 ARM64 库内相对地址；Ghidra 地址需加映像基址 `0x100000`。
反编译C中的类型、参数与局部变量由工具推断，不视为原始源码；可疑分支需核对汇编或行为证据。

## 证据基线

- 研究对象：`apk_work/original/lib/arm64-v8a/lib64ew4_Sagiri.so`。
- SHA256：`c16905a2f6d155111a1ff702f2b0f8fbad09482dcedce08785a2bf7965fe7f63`。
- Java入口在 `java/sources/com/easytech/ew4hd/wxapi/`。JADX处理464个类，有2个反编译错误，不能宣称完整恢复源码。
- 原生函数索引：`native/decompiled/functions.tsv`；选定汇编证据：`native/evidence.asm`。
- Ghidra自动分析有异常表等警告；`ok`只表示某函数成功输出C，不表示规则已理解或公式已验证。
- 本轮研究未改原始SO、游戏工作目录或现有APK，也未操作模拟器或手机。

## 已确认的运行关系

Java的 `ecRenderer.onSurfaceCreated/onDrawFrame` 调用 `nativeInit/nativeRender`；触摸从GL队列进入 `nativeTouch`。
`EW4Activity` 加载 `64ew4_Sagiri`，主要负责Android生命周期和平台接入，玩法主体在原生库中。

游戏场景初始化 `0x9ceec` 按名称注册 Area、Country、Map、Tavern、ItemStore、TriggerEvent、
ActionAssist、ActionAI、FightText、Animation、Fight、MapText、Battle；`0x9d20c`有对应清理。
这说明原版存在可辨认的组件边界，后续重构应先恢复组件之间的状态与命令关系。

已追踪链条：

```text
SceneGame 新局/读档入口 0x9d49c -> 剧本加载/状态初始化
SceneGame 每帧更新 0x9db74 -> Battle更新 0x7ec08
  -> 当前势力行动推进 0x5b70c
  -> 自动行动调度 0x7e7b8 -> ActionAI选择 0xa8e50
     -> ActionAssist候选/评分 -> 行动包 -> 0x5ba0c -> 0x5b260
  -> Fight计算 0x81634 / 战斗结算 0x825d4
```

帧更新与动画推进交织在原版实现中。新实现应把规则结算与画面时间分开，但先确认所有实际状态变化。
完整回合切换、胜负事件和存档恢复还未全部追通。

## 地图容量与寻路

- 原版地形文件分别为欧洲79×68、美洲55×76，尺寸本来就不同，不能说引擎只能79×68。
- `0x851c4`用运行时宽、高检查坐标，返回 `col + row * width`；`0x859e0`按奇偶行找六方向邻格并检查边界。
- `0x869ec`计算交错六边形网格距离；实际地形通行与路径代价另有判断，不能用直线距离替代行军回合。
- `0x76e28`分配 `0xfa28` 字节的寻路对象；`0x8db2c`使用16字节记录并在已有4000条时停止插入。
- `0x8dd7c`的处理循环也以4000为上限；`0x8dbd4`遍历六邻格，并调用地块通行/代价函数 `0x50110`。
- 因此4000是这段搜索工作区的记录上限，**不是已证明的地图总格数上限**。地图和寻路必须分别重构。

重构方向：尺寸由地图数据定义；寻路工作区按实际需求分配并有明确失败结果；
地图过大时的内存、耗时校验不得伪装成历史剧本的平衡规则。最终格数尚未定。

## 兵种名称、等级和招募

- `0x676e8`逐个比较22个固定英文兵种名并映射为0到21；非空未知名称最终返回0，会落到Militia编号。
- `0x71014`读取 `def_army.xml`，每组分配 `0x210` 字节，并按 `unit_id * 3 + grade` 写入指针。
  这对应22×3个槽位；单加XML名称无法安全扩展兵种或等级。
- 类型解析固定识别 infantry、cavalry、artillery、warship、fort，未知类型回到默认分支。
- 原始XML实际有33个直接country节点、369条army记录、22个唯一兵种名、grade值0/1/2。
  这些是现存数据统计，不代表所有势力只能各自定义这些相同记录。
- `0x77a28`的AI招募选择含固定兵种编号分支和长度18的局部候选数组；放开资源表并不足以让AI使用新兵种。
- `0x6ae84`只接受小于47的行动编号；`0x6aeac`用 `unit_id * 3 + grade` 查固定表再取行动，招募行动同样需要数据化。
- `0x5aa98`检查目标归属、地块状态、建筑/部队存在性及对应行动条件；`0x5a9f4`检查资源和行动相关条件。
- 行动编号4通过 `0x5b260`进入 `0x5ac5c`执行；具体招募、升级、补充与叠加关系仍需逐分支整理。

新实现用兵种登记表、稳定ID和数据化条件替代固定编号分支；UI、AI、招募与存档同步使用它们。
兵种种类、等级数量和实际招募叠加上限分别配置，不能承诺仅改一个常量即可全部解除。

## 叠加与战斗：已知部分及边界

`0x5318c`从当前/最大兵力比例、定义中的grade和将领能力得出攻击计算次数；
`0x81634`据此多次累计基础攻击，读取双方最小/最大攻击、将领加成、状态、射程、地形与克制项。
`0x53b94/0x53bcc`分别从兵种定义的minatk/maxatk出发加入将领修正。
部分将领加成分支会把用于加成的计数限制为5，但不能据此断言“招募最多叠5层”。

已确认叠加表现、兵力、攻击次数与等级存在关联；**准确的招募叠加上限和全部适用条件尚未确认**。
还需核对初始兵力构造、重复招募、部队合并、扣费、受损后补充、上限判断和战斗结算。
新实现应按兵种/剧本/城市条件给出明确规则，并让伤害、消耗和画面层数正确处理超过原版范围的数值。

## 收入、消耗与堆兵

- `0x71014`把XML的consumption写到兵种定义偏移 `+0x34`。
- `0x52b48`返回该消耗；持有技能编号0x16时返回0，技能名称尚需对照。
- `0x59efc`遍历势力所辖地块，取得其部队并累计上述消耗。
- `0x59358`累计地块收入，再按状态追加0/10/20/30；`0x4e948`读取建筑收入并可能乘将领修正。
- AI招募候选函数 `0x79200`调用收入、消耗和资源读取函数，再按阈值/随机数决定是否继续选候选。

因此地图尺度评估要同时观察城市收入、单位消耗、招募行为、移动耗时与损失速度。
目前尚未完整恢复收入扣费的回合时点，不声称已有可执行的经济模型或平衡数值。

## 美术与显示

- 普通贴图图集槽位64像素，但可见部分为62像素，四边各1像素防渗色边；高清对应128/124/2。
- `0x94da8`加载贴图索引，`0x94e30`用62计算网格，`0x95090`附近形成裁剪范围；
  `0x9540c/0x95410`常量分别为62和64。旧生成器的64像素步距和全局边距解释了岸线/城市的错位。
- 原城市字体只含A-Z，缺失小写与撇号，因此Xi'an不能正常完整显示。
- 新显示层使用Unicode与中文字形；旧贴图、动画和字体文件作为导入资源研究，不继承旧渲染格式限制。
- 27个BIN中有21个是BILE动画/图像容器，不能把BIN全部当成地图。动画容器目前仅识别块结构，语义未完成。

## 资源研究验证

`tools/ew4_formats.py`实现旧地形、贴图索引、PVR4444、位图字体和已验证BTL版本的独立解析与写回。
原语料441个文件逐字节往返一致：95 BTL、32字体、2地形、4贴图索引、308 PVR；
另有3个像素解码/编码往返；1323个截断、尾随或空输入被拒绝，0错误。报告在 `reports/format_audit.json`。
7项边界测试通过，包括62像素步距、高清边框、透明块、负尺寸、字体重复字形、负偏移及BTL未知字段保留。

BTL中未命名的记录继续保留为不透明字节；本体95个文件支持的版本2结构不能直接外推到所有Mod格式。
